# 后台导航与模块启停开发计划及决策备忘

初版日期为 2026-11-16，五区导航修订于 2026-11-17。核对基线为 `bcffed0b`，首批实现和回归记录见第 14 节。读者包括框架维护者、派生项目开发者和后续接手本任务的开发代理。

目标是让管理员从对应功能完成查询、操作和配置，并能在后台管理本部署已装配的可选模块。长期维护重点是模块归属明确、状态来源唯一、旧项目升级可重复执行，以及业务处理和菜单呈现各自具有准确的权限边界。

本文记录已确认的产品方向、技术设计、实施验收及仍需在部署环境核对的行为。

## 1 已确认方向与修订记录

### 1.1 已确认的产品方向

- 撤下独立的设置中心，规则、渠道、策略进入对应功能模块。较长表单可以使用模块内子页。
- 平台提供可派生的 Web 框架。订单、收款、链上充提、财务等可选能力按项目使用。
- 启停范围是整套部署，由宿主管理员在后台操作。当前交易入口主要为 Host-only。
- 已部署能力的运行期启停可以直接生效，开启前显示所需依赖，关闭前说明受影响能力。
- 停用后停止受理新业务，已受理事项、晚到回调和旧地址到账继续有处理路径。
- 财务工作区的可用状态与交易依赖的基础记账能力具有各自的含义。关闭工作区时仍需完成既有资金业务过账。
- 新项目的约定可选模块默认关闭，存量项目升级保留当前可用行为。运行期开关、原有细分开关和权限分别初始化。
- 新的菜单归属需要兼容已有角色、套餐、租户菜单、设置值和旧链接。

### 1.2 本轮收敛的技术方案

上一轮提出过统一“关闭中、排空、已关闭”流程。计划改为保存模块是否受理新业务，由订单、退款、提现等已有状态机处理存量事项。后台可链接既有异常记录，只有出现明确业务需求时才增加跨模块关停编排。

“历史只读”细化为历史查询和收尾操作分别授权。查看历史、退款、撤回、审批及异常纠正各使用原有规则。工作区停用后，必要的收尾入口保留在工作台待办或可发现的历史列表中，单据深链接继续有效。进入这些页面只要求原业务权限。

部署开关推荐使用 ABP Global Setting 的 `G` 层作为唯一持久来源。原有 ABP Feature 继续承接租户版本、配额和已存在的功能管理。这个选择由宿主作用域、依赖校验和现有通用写入接口的约束共同决定，详见第 5 节。

财务停用的首版细化建议是收起常规工作区，并阻止新建和首次提交人工账务任务，保留已受理任务的审批、纠正和基础集成记账。此处“停止新的人工任务”属于本计划的产品细化，发布前需与工作区文案及验收场景一起核对。

### 1.3 首版交付范围

首版交付功能入口归位、模块运行期状态、相应新业务检查、模块内设置授权、旧菜单迁移、派生扩展约定和回归验证。插件安装市场、运行中卸载程序集、自动删表和跨模块关停调度留给有明确需求的独立任务。

## 4 页面与导航设计

### 4.1 顶层结构

用户在 2026-11-17 确认顶层顺序为工作台、业务中心、资金与财务、平台管理、系统运维。工作台按当前授权和模块状态展示待办和常用入口。业务中心承接订单管理及派生项目的实际业务；新业务按业务归属登记，不因新增而进入单独的扩展分类。资金与财务包含收款与退款、链上充提、用户资金、会计与对账。平台管理容纳身份、租户、接入和公共管理能力。系统运维容纳日志、任务、监控和诊断。空目录按实际可访问子视图移除，个人入口放在账号菜单。

停用模块的待审核提现、失败归集和已受理调账等仍按原动作权限展示。导航归组不合并模块开关、权限或账务边界。原交易运营目录在默认模板中收起；如果管理员在其下增加了自定义业务菜单，升级保留该目录及其内容，并放在业务中心下。

页面以工作对象命名。列表、详情和配置子页共用清楚的所属模块，面包屑、标题和选中菜单由同一归属信息确定。页头配置入口可打开短表单或模块内子路由，较多内容分成有任务含义的页面。链上现有两组页签需要按工作任务收敛。

### 4.2 完整归属清单

- **用户与权限**承接用户、角色、部门、身份属性。数据范围配置挂到相应角色或业务模块，样板示例保留为开发示例。
- **登录与安全**承接登录方式、验证码、外部登录和会话策略，以及登录会话、安全日志。本人密码、MFA、通行密钥、个人设备与关联账号归个人中心。
- **租户管理**承接租户、功能版本、菜单套餐和租户策略。单租户连接串和 Feature 保留对象级入口。宿主功能管理明确标出作用范围。
- **语言与区域**承接语言、默认语言、界面翻译和默认时区。个人偏好使用个人范围。默认时区表单标出宿主或当前租户。
- **通知与模板**承接通知记录、发送渠道、邮件和短信设置、相关模板。文本模板中的其他用途继续按模板定义提供管理入口，通用模板能力可复用。
- **应用接入**承接 OIDC 应用、授权范围、令牌与授权、Webhook 订阅及现有投递记录。
- **文件、数据字典、菜单管理**保留各自的资源管理页。部署模块管理作为平台管理下的一页，提供状态、依赖、配置和历史入口。
- **审计与日志**承接接口审计和操作日志。保留策略进入对应日志页。**任务调度**承接后台任务、定时任务及已有执行记录。**运行监控**承接服务、缓存和已有诊断工具。
- **订单管理**承接订单、报价规则、超时策略及余额支付规则。我的订单保留本人范围，`?view=txns` 的本人余额流水及旧链接继续按原权限访问。用户资金工作区承接管理员按用户查询的余额与流水，单据关联入口沿用各自权限。
- **收款与退款**承接外部渠道收款、退款、查单及支付宝、微信、Stripe 的配置。余额扣款配置从订单支付方式进入，复用其所属设置数据。
- **链上充提**承接充值、提现、归集和相关监控。局部规则从局部任务进入，网络、钱包和运行控制使用模块内独立授权页面。
- **用户资金**承接用户可用/冻结余额、流水和余额调整审批。**会计与对账**承接概览、凭证、账簿调账、分录、凭证来源查询、账簿余额和对账批次。账簿余额来源于会计子账户，不能命名为用户余额核对；演示数据中的差异和核对按钮不能冒充生产功能。凭证来源查询保留 `Finance.BizDoc.View` 独立入口。
- **财务设置**从会计概览进入，按原权限显示科目、自动记账规则、会计期间和记账开关。规则与期间当前均为查看页，按实际已有能力呈现。默认侧栏不重复列出这些配置页；旧路由跳转到对应配置视图，配置专用套餐仍保留原来的入口和授权。

### 4.3 角色到达性

工作区入口权限是可访问子视图权限的并集，页面默认落到第一个获授权视图。只有配置权限的账号进入后只请求配置数据，只有记录权限的账号直接进入记录页。业务操作、设置读取、设置修改和模块启停分别检查。

模块关闭后，管理模块状态的权限仅授予启停能力。历史查询和退款等入口仍要求原权限。拥有模块管理权限不会因此获得资金操作权限。

仅有原记录或审批权限的操作员无需模块管理权限，也能找到停用后的历史与待办。配置专用套餐叶节点保留独立配置路由及页面模式，默认只加载配置。只有套餐选择了业务入口时，才把相应记录视图加入可发现的导航。套餐负责入口选择，API 继续按原业务权限授权。

### 4.4 页面呈现与交互约定

每个页面只保留一个明确的主标题。面包屑表示所属位置，列表工具栏放与当前对象有关的操作，配置入口保持在所属模块的稳定位置。设置较少时复用紧凑表单，渠道和链上运行参数使用模块内配置子页。对同一工作任务只保留一组导航，减少目录、页签与页面内按钮重复表达同一层级。

先用订单、收款、链上和仅配置角色验证布局，再推广到框架页面。检查现有 `global.less` 对 PageContainer 标题及面包屑的覆盖，统一标题责任后再改共享样式。验收包括窄屏、长中文名称、加载、空数据、无权限及模块停用状态，页面标题和返回位置不能依赖用户恰好从侧栏进入。

## 5 模块运行期设计

### 5.1 存储与职责

建议每个可选模块声明一个 `AbpAdmin.Modules.<Id>.Enabled` 设置。定义允许 `G,D`，使用专用宿主 API 写 `G/null`。定义缺省值固定为关闭，新建和升级通过初始化显式写入各自的值。初始化版本用于区分尚未完成初始化与真实关闭，接口开放前完成该准备。设置不挂 Group1，不作为客户端可枚举的通用设置，客户端从安全的模块状态 DTO 获得需要的信息。

使用既有 `ISettingManager` 保存值，采用显式 true/false。清除值恢复默认的语义不适用于模块启停。现有通用设置保存和重置都会过滤无 Group1 的项，相关测试应覆盖新增模块键。原 Feature API 使用另一种存储，模块状态没有第二份 Feature 副本。[现有写入边界](../backend/framework-app/AbpAdmin.Application/Settings/AbpAdminSettingUiAppService.cs)

共用的模块定义和状态读取接口放在各模块已有依赖链可达的框架 Domain 层，纯标识可以放在 Domain.Shared。管理 DTO 和应用服务留在 Application.Contracts 与 Application，避免业务模块为登记能力反向引用框架 Application。定义由模块贡献，包含稳定 Id、显示名称、所属域、配置入口、受支持的启用依赖和初始策略。底层框架通过定义和接口工作，业务动作的判断放在实际模块中。

拟新增的 `ModuleManagement` Contracts 与应用服务负责列出状态、预览依赖变化、提交启停和返回结果。其读写权限分别定义，写入口同时断言宿主上下文。已有宿主功能页仍承接原来的 Feature 操作，可以提供相邻入口而保持各自清晰的作用范围。

普通功能页通过应用配置贡献或已有业务读模型取得其权限范围内的最小可用性结果，避免把模块管理读取权限赋给普通操作员。启停后显式刷新动态菜单并使获授权的工作台查询失效。动态菜单加载失败或未就绪时，静态路由回退也要遵守模块状态和装配结果。

### 5.2 技术装配与启用依赖

`DependsOn` 和 ProjectReference 决定服务及契约的装配。模块启用依赖只声明启用某项业务必需同时受理的能力，按实际调用路径核实。

首批 UI 按订单、收款、链上充提、财务工作区组织。收款模块同时包含外部收款和余额扣款，新受理检查分别覆盖对应入口。订单的新支付依赖收款受理能力。链上使用的余额和账务基础服务仍然可以服务既有事项，不能仅按程序集引用推出“必须启用所有外部支付渠道”。

基础身份、菜单、授权、设置存储和被业务依赖的记账服务由部署装配维护。发布模块清单前核对每条启用依赖，重复 Id、未知依赖和循环依赖在启动验证中明确报错。

### 5.3 一次修改的提交语义

1. 页面提交目标模块、目标状态以及页面读取时的状态版本。
2. 服务在部署级修改锁内建立独立宿主事务，重新读取已提交状态，核对权限及请求中的完整目标集合。目标已全部达到时返回当前结果，不再增加版本或产生状态变更审计。仍需修改时校验预期版本，冲突要求刷新，随后验证依赖和变更集合。
3. 开启的依赖变更在一次确认中列明。关闭时若仍有已启用的依赖方，返回阻止原因及对应入口，状态保持不变。管理员先处理依赖方，再关闭被依赖能力。首版不做隐式级联关闭。
4. 状态集合和一个版本值在同一新事务中提交，修改锁持有到事务完成。失败整体回滚，重复提交已达到目标时返回当前结果。
5. 提交成功后记录操作者、状态前后值、受影响模块和关联 ID，客户端刷新模块状态、侧栏及工作台。沿用现有提交后操作日志机制，日志写入失败不回滚已提交状态。

为避免跨键缓存更新造成混合快照，权威状态读取通过 `ISettingRepository.GetListAsync(names, "G", null)` 一次读取全套少量部署键，再应用定义默认值。它与写接口共享同一存储。首版无需再加一层独立状态缓存。业务准入使用新的读取 UoW 并禁用实体跟踪，避免同一上下文返回旧实体。只在一次已获准业务操作内复用快照，菜单和工作台的预读结果不能充当准入凭证，后台每项新的受理重新读取。

ABP 10.7.1 的 `SettingManagementDbContext` 带有 `IgnoreMultiTenancy`，本仓库当前没有替换该上下文，设置仓储因此使用宿主设置库。部署状态服务仍明确宿主语义，在独立的宿主 UoW 中获取权威快照，结束后恢复调用方上下文。写接口与初始化保持同一来源。独立租户数据库属于必测场景，未来替换 Settings DbContext 时须保留这个契约。[设置数据库上下文](https://github.com/abpframework/abp/blob/ecc3c95dba1d2061c81d35121e17c3db1ef696cd/modules/setting-management/src/Volo.Abp.SettingManagement.EntityFrameworkCore/Volo/Abp/SettingManagement/EntityFrameworkCore/SettingManagementDbContext.cs)

单实例开发使用现有本地锁配置，多实例生产使用现有分布式锁配置。依赖变更并发必须覆盖多节点测试。业务准入与启停写入的并发边界另按 5.4 验收。

当前 Redis 分布式锁在 HttpApi.Host 中装配，DbMigrator 没有天然共享这份配置。P1 将所需锁配置提取为 Host 与初始化进程可复用的注册，使模块初始化与后台修改使用同名锁。核对独立 DbMigrator、Host 自动播种及多 Host 的配置后再启用并发写入，禁止在多实例环境静默退回进程内锁。

### 5.4 并发与幂等

首版将停用生效点定义为状态已提交后进行的新准入检查。已经通过检查的短事务或已经取得外部创建租约的请求可以完成，本次操作状态仍以已提交业务记录为准。页面说明这项在途语义。

新业务在首次有副作用的位置检查，查询和已有请求的合法回放先核对身份、所属业务、金额和参数一致性。支付重试可能返回已有结果，也可能重新申请渠道创建，必须在分支级区分。首版保留原查询和已实现的幂等分支，不承诺每个历史 POST 均可重放原始响应。已完成或过期交易按原状态查询恢复，不为取得结果重新发起支付。

同一次支付在报价写入或取消旧渠道之前，对订单与所选收款、余额能力做一次合并准入。已经获准的内部调用链使用本次准入快照，避免下游再次读取关闭值后中断已开始的替换流程。独立调用收款或余额入口仍自行检查。准入上下文仅在服务端当前操作内传递，不能由客户端指定，也不能沿用到另一笔业务或新一次渠道创建尝试。

保留既有唯一约束、事务和租约。网络调用不占用部署修改锁。若产品最终要求关闭提交后绝对不能完成新的受理记录，再为状态修改和持久受理建立短事务同步边界，并专项验证吞吐与锁顺序。这一严格语义不作为首版的隐含承诺。

### 5.5 开启与恢复

开启只改变模块受理状态。原有渠道状态、网络扫描、归集、提现启停和紧急停机值保留各自作用。配置不完整时页面显示缺失项和对应配置入口，后台在实际业务入口执行已有校验。

关闭保留原商户账户、凭据、验签器和网关服务的装配，确保旧交易仍能使用原渠道身份。模块状态不参与过滤这些基础服务，也不清空历史配置。

恢复使用相同状态键和原记录。重新启用不重建订单、不补造财务凭证、不重复派生充值地址。历史缺失或失败事项沿既有重试和异常处理流程恢复。

## 6 各模块的新受理和收尾边界

### 6.1 订单

- `OrderAppService.CreateAsync` 阻止新订单。
- `QuoteManager` 区分读取已有有效报价与创建、强制刷新报价。后两者受启用状态控制。
- 新支付在 `OrderAppService.StartPayAsync` 写报价之前合并检查订单及目标支付能力，`OrderPaymentManager` 的直接入口也覆盖同一规则。检查早于切换渠道取消旧单、创建渠道支付和首次余额扣款，下游沿本次获准操作继续。
- 停用后，旧订单新发起支付也按新受理处理。已经发起支付的查询、回调、取消和既有收尾继续处理。这是本计划用于避免“旧订单”含义模糊的细化。
- `OrderStatusSyncJobHandler`、收款事件处理、过期订单晚到恢复和链上充值投影继续执行，不因订单入口关闭丢掉资金事实。

当前订单详情返回收款单或余额流水 ID，支付渠道凭据主要由启动支付命令返回。首版以原查询路径恢复状态，不通过再次执行 `StartPayAsync` 获取旧凭据。若后续确需恢复仍有效的二维码或跳转链接，应单独增加按订单归属校验的纯读路径，过期凭据只回状态，不调用渠道或执行创建回调。

主要修改位置为 [订单服务](../backend/modules/platform/AbpAdmin.Ordering/Services/OrderAppService.cs)、[报价管理器](../backend/modules/platform/AbpAdmin.Ordering/Quotes/QuoteManager.cs)、[支付管理器](../backend/modules/platform/AbpAdmin.Ordering/Orders/OrderPaymentManager.cs) 和 [状态同步](../backend/modules/platform/AbpAdmin.Ordering/Jobs/OrderStatusSyncJobHandler.cs)。

### 6.2 收款与余额扣款

- `CollectionIntegrationService.CreateAsync` 在已有业务锁及租约路径内区分已有结果回放、新记录和重新取得渠道创建租约。
- 新受理关闭后，阻止首次创建和尚未获准的渠道创建调用。已取得有效创建租约的调用按既有在途语义完成。
- 首次余额扣款受状态控制。已有相同业务键的结果可回放，参数冲突仍按现有契约拒绝。
- 验签回调、查单、关单确认、退款、支付事件投递和既有冲正继续按原权限执行。对已支付的原单，在停用后首次发起必要退款仍属于收尾，可创建退款记录。回调与查单继续按原渠道及商户账户匹配。
- 余额调整留在用户资金工作区，按原授权和流程处理。收款和财务工作区停用仍允许原授权人员提交余额调整并处理已有审批，验收中核对实际余额与记账的同事务一致性。

主要位置为 [收款集成服务](../backend/modules/platform/AbpAdmin.Collection/CollectionIntegrationService.cs)、模块内 Payments 和 Balance 相关实现。阶段 P2 将这些实现中的具体分支加入入口清单。

### 6.3 链上充提

- 新地址派生在 `DepositAddressManager.GetOrDeriveAsync` 的共同入口检查，覆盖本人客户 API 和模块集成调用。
- 历史地址仍可通过关联记录查询与核对。停用时本人充值入口及对外集成入口返回模块停用，避免再次提供充值指引。
- 新提现在 `WithdrawManager` 首次冻结余额之前检查。
- 已受理提现的审批、拒绝、撤回、重试、退款、广播及人工确认继续受原来的细分开关和权限约束。
- 已有地址扫描、确认、归集和余额入账继续执行。提现模块受理状态与 `Withdraw.Enabled`、`Withdraw.Halt` 各自有明确文案。

主要位置为 [充值地址管理器](../backend/modules/platform/AbpAdmin.Collection/Chain/DepositAddressManager.cs)、[提现管理器](../backend/modules/platform/AbpAdmin.Collection/Withdrawals/WithdrawManager.cs)、[扫描管理器](../backend/modules/platform/AbpAdmin.Collection/Chain/DepositScanManager.cs) 和链上后台作业。

### 6.4 财务与基础记账

财务工作区关闭影响管理入口及新人工账务任务。拟在人工调账的新建和首次提交处检查，已受理审批、已有凭证纠正和授权历史查询继续运行。科目维护、对账操作是否属于新工作逐项列入 P4 入口清单，按用户操作含义确定。

`LedgerPostingEngine` 继续承担其他模块的集成过账与冲销。财务工作区停用不额外阻断这些操作，原 `Finance.Ledger.Enabled`、配置层 `Ledger:Enabled`、业务类型控制及账户和期间约束继续生效。保持现有业务引用、幂等和交易约束。财务工作区状态不写入 `Finance.Ledger.Enabled`，后者在会计高级运行设置中明确说明真实作用。

## 7 设置归属与服务端授权

### 7.1 共用表单与独立权限

复用 `SettingGroupPanel` 的字段、校验、掩码、提交和重置能力。模块声明具体设置名及归属页面，内置字段可以细化到 Group2。服务端按设置名核对可读、可写和 provider 范围，前端使用同一描述结果渲染。

对已认领设置，旧通用读写、专用读写及重置都经过同一归属策略。过渡兼容旧权限时采用显式映射，核对原来能够读取或修改的实际字段集合。模块配置权限只覆盖对应配置，记录查看、退款和审批继续用其各自权限。

邮件沿用 `SettingManagement.Emailing` 和测试邮件权限。时区沿用独立权限。核对返回的 Group1 Mail 元数据，避免同时显示两份 SMTP 表单或留下权限不同的旧写入路径。

### 7.2 存量与自定义设置

派生模块已有 WithUi 自动生成表单的约定需要兼容。已声明页面归属的组从所属模块进入。未声明的自定义组提供按 Group1 直达的扩展配置页，按原 ShowSettingPage、Update 和当前租户 provider 授权。即使旧扩展没有模块登记，也可从旧地址或获授权的配置入口到达。已登记模块的配置详情复用该页，进入配置不要求模块管理读写权限，配置页只展示对应组的可管理字段。

框架内置组优先完成归属，兼容页只承接尚未登记的扩展。第三方模块可以先保持旧声明，再逐步补充所属页面。移除兼容项前核对旧 URL、套餐和实际使用者。

租户上下文只展示有效作用域和来源。有读取权限但无法在当前层保存的设置显示继承或只读。迁移前后验证 Ordering、Finance、邮件和时区的保存、重置及缓存结果，不通过导航调整扩大 `G/T/U/D` provider 范围。

## 8 菜单和派生项目的长期维护

### 8.1 定义的归属

后端每个模块贡献自己的默认菜单、模块状态元数据及设置归属。中央装配确定默认一级分组和顺序。前端每个模块集中声明组件路由、页面归属、菜单编辑器选项、设置面板和工作台贡献，再由单一装配入口组合。

组件路由仍在构建时确定。运行时菜单引用稳定的路由标识和允许的地址。服务端作为模块状态和授权事实源，前端接收可用性结果，避免按数组下标或父级路径拼接业务含义。

增量重构先覆盖框架、Ordering、Collection、Ledger 和 Biz.Template。已有 API 层继续在 `web/src/abp`，按被修改的领域迁出冻结的旧服务文件。

### 8.2 稳定标识

新定义为内置菜单提供稳定 Key。可利用 Menu 现有 ExtraProperties 保存内置 Key 和最后应用的模板版本，保持菜单 GUID。已有数据只对能可靠识别的旧模板节点补标识，无法确定的记录保留为自定义记录。

现有路径仍用于旧地址兼容。路由、菜单位置、显示文案和配置存储键分别具有稳定性要求，改菜单标题不联动改设置名、权限名或公开 URL。

菜单 DTO 区分默认内置本地化 key 与管理员保存的自定义标题。默认名称按稳定 key 翻译，自定义名称直接使用保存值，重挂父级不改变本地化 key。宿主和租户的改名结果在中文、英文及位置调整后均需可见。

### 8.3 模板更新和用户定制

升级时按已知旧模板与当前记录逐字段比较。仍与旧默认相同的字段可以更新到新默认，用户已更改的父级、标题、顺序、隐藏、停用或权限绑定保留。未来模板升级复用同一规则。

父级比较使用归一化后的模板 Key，并核对整条旧祖先链的有效启用状态和权限行为。用户停用了祖先目录时，即使子节点本身仍为默认值，也不能通过迁移把子节点移动到启用目录而重新暴露。隐藏提升与停用剪枝分别建夹具。无法确定继承意图的节点保留原可达性并记录待核对项。

宿主的现有 SeedHostTemplateAsync 会覆盖部分字段，因此需要一起调整它的后续同步策略，防止一次性迁移保留的定制在下次启动时又被覆盖。新库直接使用新模板，老库走版本化升级。

对自定义路径不能仅凭绑定某个业务权限推断模块归属。内置路由和别名采用明确映射，自定义菜单可以显式选择所属已注册模块。没有归属的自定义项仍使用原可见性逻辑，实际业务 API 继续检查模块状态。

内置路由及旧别名另有明确的宿主或租户作用范围，不能仅依赖当前父目录判断。移动目录或退役旧模板时仍保留旧别名的 Host-only 判定，路由和端点各自保留守卫。覆盖旧租户快照中的 `/web3/*`、`/collection/*` 和 `/configuration/payments`，避免迁移后把宿主入口展示给租户。

## 9 初始化 菜单迁移与回滚

### 9.1 新建与升级模式

新部署默认关闭与旧部署保持可用需要不同初始化输入。完成 EF 迁移后的表存在性、用户数量和业务记录数量都不足以可靠判断安装来源。

推荐在首次配置的安装入口明确传入 `New` 或 `Upgrade` 意图，由安装配置或命令参数持续提供直到初始化成功，再与模块状态一起持久记录。正常重启、反复 seed 和后续升级读取已保存的初始化版本，管理员已设置的值优先。

现有项目缺少新标记时采用升级兼容策略。新项目创建流程、初始化脚本和全新体验栈设置 New 意图。直接使用自建部署流程时，文档明确其首次初始化选择。禁止把新模式写成所有已有部署都会自动继承的全局默认。

初始化失败重试持续使用原始意图，不能因第一次事务失败且缺少标记而转成 Upgrade。初始化只在宿主执行，由单一协调者使用后台修改的同名锁，状态行、初始化标记和状态版本同事务写入。通过 `forceToSet:true` 显式保存与默认值相同的值，避免被默认值优化清除。

跨模块装配列表变化时，只初始化首次加入的模块，默认关闭或按该项目显式初始化声明处理。已经完成升级的项目后来新增模块，不能继承首次 Upgrade 的保持开启策略。重新装配已有持久值的模块保留管理员原选择，移除模块定义时保留旧值但不形成可访问入口。

### 9.2 菜单升级

1. 固化当前默认模板、旧模板和自定义数据的测试夹具，记录菜单 GUID、套餐引用和有效权限。
2. 新页面与旧地址适配先上线，验证原路径携带的 `view`、记录 ID、筛选条件和返回位置。
3. 按旧内置标识及指纹映射宿主与租户菜单。先移动明确归属的子节点，再处理旧目录。
4. 对 `/administration/settings` 和 `/configuration/payments` 等一对多拆分叶节点，先保存可达兼容入口，再按原有能力范围映射套餐。配置专用套餐和历史自定义节点保留专用子路由身份及 GUID，映射到模块内配置模式。只选配置的节点不能直接变成默认加载记录的工作区根。
5. 复用已有菜单 GUID。扩展新叶节点时记录对应关系，旧模板外节点及自定义后代按原行为保存。
6. 每个租户迁移可重复执行，有完成版本和失败记录。独立数据库遵守现有隔离及模板可用性限制，在宿主和目标租户上下文各自执行。
7. 日常模块启停只影响运行时计算。菜单行、套餐和权限值不会随每次开关被反复重写。

套餐应用的菜单重置流程保留其原用途，升级使用定向迁移。目录包含自定义子项时保留可达的自定义父结构，避免将其整棵隐藏或上浮造成导航突变。

### 9.3 发布与回滚

先发布旧新入口均可访问的兼容代码，完成数据迁移再切换默认侧栏。实际部署中的前后端版本必须配套验证。模块状态检查分布在各业务实例，混合新旧后端期间无法保证旧实例执行新开关，运行期管理入口应在支持该策略的版本完成切换后开放。

回滚到仍理解新状态和别名的兼容版本。更老版本会忽略模块停用值，回滚评估必须列明这一结果。菜单迁移记录变更前值，用于受控恢复布局，避免用套餐重置代替回滚。

所有数据库变化沿现有 EF Core 和模块迁移入口交付。数据升级应在新库、既有数据库和失败重试场景中演练。

### P0 固化规格和测试基线

### P1 部署状态基础与模块登记

新增框架模块定义、宿主状态接口、专用授权、依赖检查、事务版本和初始化。模块自行提供定义，宿主装配读取定义。统一 Host 与 DbMigrator 的模块变更锁注册和初始化互斥。先在状态和测试中接通，启停入口在业务检查齐全后开放。

### P2 订单和收款的端到端启停

接通新订单、报价创建、支付启动、收款创建及余额扣款检查。保留已有结果回放、回调、退款、出箱和状态同步。前端状态、按钮和服务端失败响应对齐。

验收采用完整场景。停用时新请求不产生扣款或新渠道单，旧支付结果能够确认，既有幂等分支不产生重复副作用，其他重试可通过原查询恢复交易状态。停用和请求交错时符合 5.4 的准入语义。

用户确认资金与财务按「收款管理、用户资金、钱包与链网、会计与对账」组织。根目录保持工作台、业务中心、资金与财务、平台管理、系统运维。此轮重组页面和关联读取，不改变支付、充值入账、归集、提现、退款或会计过账的写入流程。
